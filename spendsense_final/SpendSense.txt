SpendSense — Transaction Intelligence Model
Lightweight On-Device Transaction Classification Model

SpendSense is a lightweight machine learning system designed to understand and categorize financial transactions from parsed transaction data.

The model is designed specifically for mobile deployment, with the final inference model exported in TensorFlow Lite (.tflite) format.

Unlike a large language model or generative system, SpendSense uses a compact supervised deep learning architecture optimized for:

Fast inference
Low memory consumption
Offline mobile execution
Structured transaction classification
Privacy-preserving on-device inference
1. Problem Statement

Financial transactions can originate from multiple sources such as:

Bank SMS
UPI notifications
Card transactions
Bank statements
Payment applications

A raw transaction may look like:

ICICI Bank Acct XX888 debited for Rs 45.00 on 02-Aug-26;
BHUPENDRA DILIP credited.
UPI:621412961083.
Call 18002662 for dispute.
SMS BLOCK 888 to 9215676766.

However, raw transaction messages are inconsistent and noisy.

Different banks use different formats, transaction descriptions may vary, and merchant names may not always be explicitly standardized.

Therefore, SpendSense follows a pipeline-based architecture.

Raw Financial Evidence
        │
        ▼
Transaction Parsing Layer
        │
        ▼
Structured Transaction Object
        │
        ▼
SpendSense Classification Model
        │
        ├── Merchant Prediction
        │
        └── Category Prediction
        │
        ▼
Final Categorized Transaction

The machine learning model is not responsible for parsing financial SMS.

Parsing and extraction are handled before the model.

This separation is intentional and important for reliability.

The SpendSense model receives the transaction narration after preprocessing.

Example:

ICICI Bank Acct XX888 debited for Rs 45.00 on 02-Aug-26;
BHUPENDRA DILIP credited.
UPI:621412961083.

Before inference, the text undergoes deterministic preprocessing.

Raw Transaction Text
        │
        ▼
Lowercase Conversion
        │
        ▼
Whitespace Normalization
        │
        ▼
Character-Level Tokenization
        │
        ▼
Integer Token Sequence
        │

Padding / Truncation
        │
        ▼
Fixed Length Input

The final model input is:

Shape: [1, 128]

Data Type: int32

Example representation:

[12, 45, 19, 19, 23, 67, 8, 91, ...]

Each integer represents a character from the learned vocabulary.

4. Why Character-Level Tokenization?

Traditional NLP systems often use word-level tokenization.

For example:

BHUPENDRA DILIP

would be treated as words.

However, financial transaction data is highly inconsistent.

Examples include:

NETFLIX
Netflix India
NETFLIX.COM
NETFLIX*BILLING
NFX PAYMENT
NETFLIX MUMBAI

Similarly, merchant names may appear as:

SWIGGY
SWIGGY INSTAMART
SWIGGY*ORDER
SWIGGY ONLINE

Bank messages also contain:

Account masking
Transaction IDs
UPI references
Abbreviations
Special characters
Bank-specific formatting
Misspellings
Merchant variations

Character-level tokenization is more robust for this type of semi-structured financial text.

Advantages
Handles spelling variations
Handles abbreviations
Handles unknown words
Handles transaction IDs
Handles bank-specific formatting
Requires a small vocabulary
Easy to reproduce on mobile
TFLite compatible
No external tokenizer dependency

The mobile application only needs:

vocabulary.json
+
tokenizer_config.json

to reproduce the exact preprocessing pipeline.

6. Detailed Architecture
6.1 Input Layer

The model receives a fixed-length sequence.

Input Shape: (128,)
Input Type: int32

Example:

[45, 12, 78, 91, 23, 4, 0, 0, 0, ...]

Where:

0 = Padding Token
1 = Unknown Character
2+ = Vocabulary Characters
6.2 Embedding Layer

The embedding layer converts integer character IDs into dense numerical vectors.

Vocabulary ID
      │
      ▼
Embedding Layer
      │
      ▼
Dense Character Representation

Configuration:

Embedding Dimension: 64

Instead of treating characters as independent IDs, the model learns relationships between character patterns.

6.3 Multi-Scale CNN

The model uses three parallel convolution branches.

Conv1D Kernel Size = 3
Conv1D Kernel Size = 5
Conv1D Kernel Size = 7

Each branch learns different pattern sizes.

Kernel Size 3

Captures short character patterns.

Examples:

upi
pay
deb
Kernel Size 5

Captures medium patterns.

Examples:

swigg
netfl
cred
Kernel Size 7

Captures longer transaction signatures.

Examples:

netflix
zomato
amazon

This allows the model to detect merchant and transaction patterns at multiple scales.

7. Why CNN Instead of LSTM or Transformer?

Several architectures were considered.

Architecture	Advantages	Limitations
LSTM	Sequence understanding	Slower inference
GRU	Smaller than LSTM	Sequential computation
Transformer	Powerful NLP architecture	Heavy for mobile
BERT	High accuracy	Too large for lightweight deployment
CNN	Fast, compact, parallelizable	Less global context
Multi-Scale CNN	Fast + lightweight + pattern detection	Selected

The transaction classification problem is primarily a pattern recognition problem.

For example:

NETFLIX
ZOMATO
SWIGGY
AMAZON
UBER
UPI
POS
NEFT

These patterns do not necessarily require deep language understanding.

CNNs are highly effective at detecting local patterns.

Therefore, the selected architecture provides a good balance between:

Accuracy
+
Model Size
+
Inference Speed
+
Mobile Compatibility
8. Multi-Task Learning Architecture

Instead of training completely separate models, SpendSense uses a shared neural network.

                Shared Feature Extractor
                        │
                        │
                ┌───────┴────────┐
                │                │
                ▼                ▼
         Merchant Task      Category Task

The model learns common transaction features and then uses separate output heads.

Output Head 1
Merchant Classification
Output Head 2
Category Classification

For example:

Input:
"Payment made to ZOMATO"

            Shared Model
                  │
        ┌─────────┴─────────┐
        ▼                   ▼
    Merchant             Category
        │                   │
        ▼                   ▼
    ZOMATO              Food & Dining
9. Why Multi-Task Learning?

Merchant and category information are strongly related.

Example:

Merchant: NETFLIX

Possible Categories:
- Entertainment
- Subscription
- Digital Services

Another example:

Merchant: SWIGGY

Possible Categories:
- Food & Dining
- Groceries

The same transaction patterns contribute to both tasks.

Training separate models would duplicate feature extraction.

Multi-task learning allows:

Transaction Pattern
       │
       ▼
Shared Representation
       │
       ├── Merchant Knowledge
       │
       └── Category Knowledge

Advantages:

Reduced model size
Shared learning
Faster inference
Lower mobile memory usage
Potential improvement in generalization

14. Dataset Splitting Strategy

A standard random train/test split is insufficient for merchant classification.

Consider:

Merchant: Buddy

Training Samples: 0
Validation Samples: 10

The model would be asked to predict a class it has never seen.

This causes errors such as:

ValueError:
y contains previously unseen labels

Therefore SpendSense uses a merchant-aware splitting strategy.

Dataset
   │
   ▼
Group Transactions by Merchant
   │
   ├── Merchant A
   │      ├── Train
   │      ├── Validation
   │      └── Test
   │
   ├── Merchant B
   │      ├── Train
   │      ├── Validation
   │      └── Test
   │
   └── Rare Merchant
          │
          └── Training Only

This guarantees:

Every merchant evaluated during validation or testing has already appeared in the training dataset.

15. Closed-Set Classification

The current model operates as a closed-set classifier.

This means the merchant output layer contains a fixed list of known merchants.

Example:

Known Merchant Classes

ZOMATO
SWIGGY
NETFLIX
AMAZON
UBER
...

The model predicts one of these known classes.

However, real-world transactions may contain previously unseen merchants.

Example:

Input:
PAYMENT TO NEW_LOCAL_STORE_123

The model should not blindly classify it as:

ZOMATO

Therefore production deployment should include a confidence threshold.

Example:

Prediction:
Merchant = ZOMATO
Confidence = 0.31

Since confidence is low:

Final Merchant = UNKNOWN

Recommended production logic:

if confidence >= threshold:
    accept_prediction
else:
    UNKNOWN

This is important for preventing incorrect merchant assignments.

20. Why Integer Inputs Were Used

The model does not accept raw strings directly.

Instead:

Transaction Text
        ↓
Tokenizer
        ↓
Integer Sequence
        ↓
TFLite Model

This architecture was selected because text preprocessing layers can introduce compatibility issues during TFLite conversion.

Separating preprocessing provides:

Reliable TFLite conversion
Deterministic mobile inference
Smaller deployment complexity
No TensorFlow text dependency
Easier debugging
Identical preprocessing across training and mobile inference
21. Model Accuracy Goal

The target performance objective is:

Overall Category Accuracy:
94% – 97%

However, accuracy must not be evaluated alone.

The evaluation pipeline includes:

Accuracy
Precision
Recall
Macro F1 Score
Weighted F1 Score
Classification Reports
Confusion Matrices
Incorrect Prediction Analysis

For category classification, Macro F1 is particularly important because it prevents large classes from hiding poor performance on smaller categories.

22. Evaluation Strategy

The final test set is never used during training.

Training Set
      │
      ▼
Model Learning

Validation Set
      │
      ▼
Hyperparameter Monitoring
Early Stopping
Learning Rate Adjustment

Test Set
      │
      ▼
Final Performance Evaluation

The final evaluation checks both:

Keras Model Predictions

and

TFLite Model Predictions

This ensures that conversion to TensorFlow Lite does not significantly alter model predictions.

23. Production Confidence Strategy

For production use, predictions should not always be accepted blindly.

Recommended architecture:

Model Prediction
       │
       ▼
Confidence Score
       │
       ├── High Confidence
       │        │
       │        ▼
       │   Accept Prediction
       │
       └── Low Confidence
                │
                ▼
        UNKNOWN / REVIEW

Example:

Merchant Prediction

NETFLIX
Confidence: 97%

Result:

Accept

Example:

Merchant Prediction

NETFLIX
Confidence: 28%

Result:

UNKNOWN

This prevents the closed-set classifier from forcing incorrect classifications for unseen merchants.

Parsing extracts facts. Machine learning recognizes patterns. The final system combines both to produce an intelligent structured transaction record.
